# Pi Compound Engineering Native UX Improvements

## Problem

Compound Engineering already supports Pi through the converter-backed `--to pi` target. The remaining gap is not a separate plugin: it is improving this repository's Pi output so Pi users get a clearer, safer, more native experience after installing Compound Engineering.

## Goals

- Keep this work inside the existing `compound-engineering-plugin` repository.
- Preserve the current converter-backed install path.
- Add Pi-native setup/status affordances without forking the skill and agent corpus.
- Make Pi-specific dependency and subagent limitations visible at runtime and in docs.
- Strengthen tests around the generated Pi artifact tree.

## Non-goals

- Do not create a separate Compound Engineering Pi plugin repository.
- Do not manually copy or fork the 37 Pi-compatible skills or 43 agents.
- Do not replace `pi-subagents` or `pi-ask-user` unless upstream Pi gains built-in equivalents.
- Do not change Claude, Codex, Gemini, Kiro, or OpenCode behavior except where shared converter code already applies.

## Packaging shape decision

Use the existing upstream Pi target shape:

- `.pi/skills/<skill>/SKILL.md` for CE skills.
- `.pi/agents/<agent>.md` for CE agents consumed by `pi-subagents`.
- `.pi/prompts/*.md` only for plugin command conversion; current CE workflows are skills, so this remains empty for Compound Engineering unless commands are later added.
- `.pi/compound-engineering/install-manifest.json` for managed artifact tracking and cleanup.
- `.pi/compound-engineering/mcporter.json` when MCP servers are declared.
- Root `AGENTS.md` managed block for Pi compatibility notes.
- Add a generated `.pi/extensions/compound-engineering/index.ts` companion extension for Pi-only setup/status/help.

The companion extension should be generated by `convertClaudeToPi`, written by `writePiBundle`, and tracked in the existing install manifest just like other managed Pi artifacts.

## Source layout decision

Reuse the existing source-of-truth layout:

- Skills stay under `plugins/compound-engineering/skills/*/SKILL.md`.
- Agents stay under `plugins/compound-engineering/agents/*.md`.
- Pi conversion behavior stays in `src/converters/claude-to-pi.ts`.
- Pi writing/cleanup behavior stays in `src/targets/pi.ts`.
- Pi types stay in `src/types/pi.ts`.
- Pi tests stay in `tests/pi-converter.test.ts` and `tests/pi-writer.test.ts`, with an added end-to-end fixture test if needed.

Do not create parallel Pi-specific copies of CE skill or agent prose. If a skill needs Pi-specific guidance, update the source skill prose with cross-platform wording so all targets remain coherent.

## Implementation units

### U1: Generate a Pi companion extension

Files:

- Modify: `src/converters/claude-to-pi.ts`
- Modify: `src/types/pi.ts` only if needed
- Modify: `tests/pi-converter.test.ts`

Approach:

- Add one generated extension file to the Pi bundle for the Compound Engineering plugin.
- Register `/ce-status`, `/ce-setup-pi`, and optionally `/ce-help`.
- Keep the extension dependency-free and TypeScript-only.
- Use conservative filesystem checks for expected `.pi/skills`, `.pi/agents`, and managed manifest paths.

Verification:

- Converter tests assert the extension is emitted for `compound-engineering`.
- Converter tests assert non-CE fixture behavior if we choose to emit only for CE.

### U2: Write extension directory artifacts correctly

Files:

- Modify: `src/targets/pi.ts`
- Modify: `tests/pi-writer.test.ts`

Approach:

- Ensure extension names containing paths such as `compound-engineering/index.ts` are written safely under `.pi/extensions/compound-engineering/index.ts`.
- Keep path traversal protections.
- Ensure managed manifest cleanup removes extension subtrees created by prior installs.

Verification:

- Writer test covers nested extension output.
- Reinstall test confirms removed nested extensions are cleaned up.

### U3: Improve Pi compatibility docs and managed block

Files:

- Modify: `src/targets/pi.ts`
- Modify: `README.md`
- Modify: `plugins/compound-engineering/README.md` if user-facing behavior changes

Approach:

- Update the managed AGENTS block to mention `/ce-status` and `/ce-setup-pi`.
- Keep prerequisite install commands visible.
- Document that Pi support is converter-backed and enhanced by the companion extension.

Verification:

- Writer tests assert AGENTS block includes extension commands and dependency notes.

### U4: Add Pi-specific safety guidance where it matters

Files:

- Modify: `plugins/compound-engineering/skills/ce-work/SKILL.md`
- Possibly modify: `plugins/compound-engineering/skills/ce-code-review/SKILL.md`
- Possibly modify: `plugins/compound-engineering/skills/ce-doc-review/SKILL.md`

Approach:

- Keep guidance cross-platform, but make Pi's shared-directory subagent behavior explicit where execution safety depends on it.
- Prefer serial subagents when file overlap exists and worktree isolation is unavailable.
- In shared-directory mode, instruct subagents not to stage, commit, or run full project test suites.

Verification:

- Existing skill contract tests still pass.
- Add targeted text tests only if there is an existing pattern for skill prose invariants.

### U5: End-to-end Pi fixture install test

Files:

- Modify: `tests/pi-writer.test.ts` or add `tests/pi-install-e2e.test.ts`

Approach:

- Load `plugins/compound-engineering`.
- Convert to Pi.
- Write to temp root.
- Assert representative skills, agents, manifest, AGENTS block, and companion extension exist.

Verification:

- `bun test tests/pi-converter.test.ts tests/pi-writer.test.ts` passes.

## Success criteria

- `bun run src/index.ts install ./plugins/compound-engineering --to pi --pi-home <tmp>` writes skills, agents, managed manifest, AGENTS block, and companion extension.
- `/ce-status` and `/ce-setup-pi` are available after Pi reload.
- Existing Pi skills remain sourced from `plugins/compound-engineering/skills`.
- Pi users can discover required dependencies and known subagent safety constraints without reading repo internals.

## Deferred richer Pi-native ideas

Defer these until the MVP companion extension is validated in real Pi sessions:

- Status widgets for active CE workflow phases.
- Custom renderers for review findings.
- A `/ce-cycle` command that guides brainstorm -> plan -> work -> review -> compound.
- Automatic detection of the latest CE plan or review artifact from the extension.
- Deeper integration with any future Pi-native task-tracking or subagent-isolation primitives.
